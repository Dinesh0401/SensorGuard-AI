## 2. Target Cohort & Informed Consent Protocol

- **Sample Size & Profile:** **5 to 10 technical practitioners** (air-quality analysts, environmental monitoring engineers, urban civil/reliability engineers, or ML uncertainty practitioners). General public/clinical recruitment is out of scope.
- **Exclusion Boundaries:** Explicitly excludes medical, clinical, or emergency-dispatch triage decisions.
- **Informed Consent Script Summary (Must Be Signed/Acknowledged Before Session):**
  1. **System Role:** SensorGuard AI is a research and private staging prototype forecasting hourly PM2.5 uncertainty bands (`µg/m³`) across UK AURN monitoring locations.
  2. **Data Provenance Notice:** Sessions demonstrate archived Q1 2024 data (`archived_historical`) or bounded opt-in shadow feeds (`shadow_live`) clearly labeled in the UI banner—never public real-time health advisories.
  3. **Model & Coverage Caveats:** Active forecasts come from Static `SAGEForecaster v1.0.0`; prediction intervals carry conditional coverage expectations under MAR/MCAR checks and **do not guarantee nominal 90% coverage under arbitrary missing-not-at-random (MNAR) sensor dropouts**.
  4. **Data Collection:** Sessions record task completion accuracy, anonymised think-aloud friction notes, and post-task questionnaire scores; raw notes omit PII and participants may withdraw at any point.

## 3. Guided Dashboard Evaluation Tasks (5 Tasks / ~25 Minutes)

Participants use the non-public UI (`apps/web`) while an observer records task outcomes without coaching:

1. **Task 1 — Provenance & Operating Mode Identification:**
   - *Prompt:* "Identify which data source and operating mode the dashboard is currently showing, and which model class generated the forecast intervals."
   - *Expected Ground-Truth Answer:* Archived Q1 2024 UK AURN (`archived_historical` mode, `is_archived_pilot=True`) generated by primary `SAGEForecaster` (`v1.0.0`), while `AdaptiveSAGEForecaster` is explicitly marked **Shadow Research (Not Served)** (`promoted_to_primary=false`).
2. **Task 2 — Distinguishing Abstention (`ABSTAIN`) from Confirmed Hardware Breakage:**
   - *Prompt:* "Examine a station showing `ABSTAIN (stale_sensor_history)` or missing hours in the forecast/observation series. Does SensorGuard confirm that the physical sensor hardware is broken?"
   - *Expected Ground-Truth Answer:* **No.** `NO_REPORT` / >12h staleness indicates missing recent upstream telemetry (`observed_at` gap), which may reflect upstream feed delay, API cutoff (e.g., 6 EEA feeds inactive at snapshot), communications interruption, or physical maintenance—never confirmed hardware destruction.
3. **Task 3 — Interpreting Freshness States (`HEALTHY` vs `LATE` vs `NO_REPORT`):**
   - *Prompt:* "Compare `observed_at` vs `fetched_at` freshness indicators and explain what changes between `3h–12h` delay and `>12h` silence."
   - *Expected Ground-Truth Answer:* `HEALTHY` (`<= 3h`), `LATE` (`3h–12h`, cautious publication), and `NO_REPORT` (`> 12h`, forecast interval abstained).
4. **Task 4 — MNAR Sensitivity & `D_sens` vs Real-World Guarantees:**
   - *Prompt:* "Inspect sensitivity slider / $\Gamma$ bounds in the Reliability Simulator Lab (`SIMULATED OUTAGE` vs `NATURAL OBSERVED`). Do wider $\Gamma=2.0$ bounds guarantee 90% coverage during arbitrary unmeasured real-world outages?"
   - *Expected Ground-Truth Answer:* **No.** $\Gamma$-bounds quantify bounded log-odds informative missingness sensitivity under simulated regimes; arbitrary unrestricted MNAR shifts remain unidentifiable without auxiliary measurements.
5. **Task 5 — Offline Demo Fixture vs Connected Backend Separation:**
   - *Prompt:* "Toggle Demo Mode and inspect the header banner and footer. How can an operator guarantee they are not mistaking offline demo fixtures for live backend API telemetry?"
   - *Expected Ground-Truth Answer:* Explicit `DEMO MODE ACTIVE` warning badge + footer (`Offline Demo Fixtures`), vs `FastAPI Connected` + SHA-256 verification status + Kill-Switch readiness card.

## 4. Quantitative Comprehension Metrics & Survey Instrument

- **Go/No-Go Usability & Comprehension Gate Criteria:**
  - $\ge 80\%$ participant accuracy on **Task 2** (distinguishing upstream reporting gaps from confirmed sensor failure) and **Task 1** (identifying Static vs Shadow model + operating mode).
  - $100\%$ correct identification on **Task 5** (zero confusion between offline demo fixtures and live API connectivity).
  - Median NASA-TLX / single-ease rating $\ge 4 / 5$ on understanding why intervals widen or abstain.
- **Post-Task Survey (1–5 Likert + Open Free-Text):**
  1. *"The distinction between active Static SAGE predictions and unpromoted shadow research models is clear."* (1–5)
  2. *"I understood when missing sensor reports trigger an abstention vs cautious wider interval."* (1–5)
  3. *"The dashboard avoided misleading me into treating archived Q1 2024 data as live real-time readings."* (1–5)
  4. *"What single label, chart visual, or warning could most improve operational trust?"* (Open text)

---

## 5. Issue Triage & Remediation Workflow

Every participant comprehension error or UI friction finding is logged cleanly before any pilot expansion:
1. Capture Task ID, UI component/endpoint affected, severity (`P0` Safety/Misinterpretation Risk, `P1` Comprehension Confusion, `P2` Cosmetic).
2. Any `P0` misinterpretation (e.g., mistaking `archived_historical` for live telemetry, or `ABSTAIN` for medical safety/physical hardware certainty) automatically blocks progression to `validated_live`.
3. Update `apps/web/app/page.tsx` wording + Playwright E2E assertions in `apps/web/e2e/dashboard.spec.ts` to regress-protect the clarified copy, then re-test with subsequent cohort batch.
